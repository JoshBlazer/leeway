# M3 walkthrough: escrow end to end

**Exit check:** two offline clients spend within their leases, reconnect, and the invariant holds. An overspend becomes provisional and resolves correctly.

**Result:** Met. Everything here runs over real HTTP, real Datasync 10.1.2, and real SQLite files on both sides.

```
dotnet test --project tests/Leeway.Integration.Tests
python scripts/adapter-sabotage.py
```

## The exit check

| Part | Test |
|---|---|
| Two offline gates spend, reconnect, invariant holds | `Two_offline_gates_spend_within_their_leases_reconnect_and_the_invariant_holds` |
| Overspend accepted when the pool can fund it | `Overspending_offline_becomes_provisional_and_is_accepted_while_the_pool_can_fund_it` |
| Overspend rejected when it cannot, with nothing changed | `Overspending_offline_is_rejected_when_the_pool_cannot_fund_it_and_the_rule_still_holds` |

The first test: capacity 25, two gates lease 10 each, and both spend all 10 offline. Each gate's wallet reaches 0 and the server has heard nothing. After reconnecting, the ledger shows 20 consumed, it is conserved, there is no overdraft, and the server and both gates show 5 remaining.

## Using it

```csharp
public class Zone : OfflineEntity
{
    [Escrow(Min = 0, Lease = 10)] public int RemainingCapacity { get; set; }
}

await client.RequestLeaseAsync<Zone>("north", z => z.RemainingCapacity);
await client.SyncAsync();

// No signal needed from here on.
SpendResult result = await client.TrySpendAsync<Zone>("north", z => z.RemainingCapacity, 1);
// result.Status: Confirmed (within the lease) or Provisional (the server decides on reconnect)

await client.SyncAsync();
OperationOutcome? outcome = await client.OutcomeOfAsync(result.OperationId);
```

## Do the tests catch anything?

All 25 new tests passed first time, which I did not trust. So I broke each protection in the adapters on purpose. **On the first run, three of the eight went unnoticed:**

| Survivor | Why no test noticed | Added |
|---|---|---|
| Client trusts `PushResult` | The fault also failed the pull, which reported offline by accident | A fault that fails only pushes |
| Server ignores `Observed` | The device's HLC covered the simple case | A test at the drift limit, where only `Observed` helps |
| Settling dropped from the view | Rows keep their local view, so counters were fine, and only escrow figures were exposed | A test of a spend after an acknowledged spend |

The final result, from `scripts/adapter-sabotage.py`:

```
Server stamps with the plain clock (C19): CAUGHT by 12 test(s)
Server does not check for a replay: CAUGHT by 4 test(s)
Server ignores what the writer had seen: CAUGHT by 1 test(s)
Client drops settling operations from the view: CAUGHT by 2 test(s)
Client trusts PushResult (C24): CAUGHT by 1 test(s)
Wallet update has no balance check: CAUGHT by 5 test(s)
Client does not reapply local changes after a pull: CAUGHT by 1 test(s)
No ServerWins resolver on the operation table: CAUGHT by 4 test(s)
Caught 8 of 8.
```

Along the way, this tool misled me twice, and both are recorded so the lesson stays. One run reported a "hang" that was my own time limit: the suite takes about 110 s anyway. Another reported four false survivors, because a bad flag meant no tests ran. The script now treats a run with no test summary as no result.

## Limits

These are also in `docs/design/escrow-protocol.md`.

- **Write-off can break the rule,** and that is reported as an overdraft rather than hidden (`A_spend_from_a_written_off_gate_is_reported_as_an_overdraft`).
- **No device authentication.** `Device` is whatever the client claims, so an application must authenticate devices.
- **A modified client is out of scope.** The guarantee assumes the wallet code runs as written.
- **SQLite and one server process only.** The server's write gate is in-process.
- **Nothing is pruned.** The op table, outbox, and ledger state grow.
- **A refused operation stays queued and is retried,** with no way yet to discard it. It does not block pulls.
- **Local write speed is unmeasured.** Tests suggest that it is not instant, and a benchmark is needed.
- **The wallet is only tested from one process.** The balance check is one SQL statement, which should hold across processes, but that is untested.
- **GateKeeper does not use this yet.** The sample is still the M0 spike, and moving it is M6.
