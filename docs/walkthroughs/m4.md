# M4 walkthrough: field-semantic conflict resolution

**Exit check:** concurrent offline edits merge per field instead of whole-row wins.

**Result:** Met.

```
dotnet test --project tests/Leeway.Integration.Tests
```

The test is `Concurrent_offline_edits_to_one_row_merge_per_field_instead_of_whole_row_wins`.

## Before and after

Two gates edit the same row offline, on the same transport.

| | Datasync's default (M0, C05, C06) | With Leeway |
|---|---|---|
| Different fields | One gate's push is rejected with a 412 | Both edits are kept |
| Counter | Whole-row, so one total is lost | 5 + 7 = 12 |
| Set | One whole list is lost | Both flags are kept |
| The losing device | Stuck, with pulls blocked for that table | Nothing to resolve |

## Using it

```csharp
public class Zone : OfflineEntity
{
    [Counter]        public int CheckIns { get; set; }
    [LastWriterWins] public string? Notes { get; set; }
    [AddWinsSet]     public string? FlagsJson { get; set; }   // A JSON array, for now: see ADR-0015.
}

await client.EditAsync<Zone>("north", e => e
    .Set(z => z.Notes, "Turnstile 3 jammed")
    .Add(z => z.CheckIns, 5)
    .AddToSet(z => z.FlagsJson, "vip"));

await client.SyncAsync();
```

## This differs from the brief's wording

The brief describes a client-side "field-semantic conflict resolver". M0 showed a resolver's merged write is unconditional and can lose a concurrent update (C10), so ADR-0012, which you accepted, moved the authoritative merge to the server. The exit check is met without any merging in a resolver: the only client resolver is `ServerWins` on the op table, where a 409 means "already applied".

## What else is tested

| Behaviour | Test |
|---|---|
| Local changes survive a pull that arrives before they are pushed | `A_value_written_offline_shows_locally_at_once_and_survives_a_pull_before_it_is_pushed` |
| The next add does not lose an increment (the simulator's bug) | `An_add_after_a_push_and_before_a_pull_does_not_lose_an_increment` |
| A concurrent add beats a remove, and a remove that saw the add wins | `A_concurrent_add_beats_a_remove_and_a_remove_that_saw_the_add_wins` |
| A slow clock still beats what it saw | `A_device_with_a_slow_clock_still_beats_a_value_it_has_seen` |
| A write beats a seen value at the drift limit | `A_write_that_saw_a_value_at_the_drift_limit_still_beats_it` |
| A clock a day fast cannot win every merge | `A_device_with_a_fast_clock_cannot_win_every_merge` |
| Simultaneous pushes from four devices lose nothing | `Simultaneous_pushes_from_many_devices_lose_nothing` |

## Limits

- **`An_add_after_a_push_...` does not protect the counter by itself.** Sabotage showed rows keep the local view, so that test passes without the settling logic. The escrow test next to it is what covers that logic.
- **Deleting entities is not implemented.**
- **Registers keep one write.** Concurrent writers to one text field do not merge, and the losing value is not reported.
- **Add-wins is a policy,** and it is wrong for cases such as revoking access.
- **Rougher than the brief's sketch.** It uses reflection, `string` sets, and `client.EditAsync`. M5 is where the generator improves this (ADR-0015).
- **An entity created offline has no escrow.** Ledgers are created on the server with `CreateEntityAsync`.
- **Both classes must carry matching attributes.** The client and server each have their own entity class. Nothing checks they agree until M5.
