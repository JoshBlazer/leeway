# M5 walkthrough: generator and analyzer

**Exit check:** attributes produce merge code (snapshot tests), and analyzer diagnostics and code fixes are tested.

**Result:** Met.

```
dotnet test --project tests/Leeway.Generators.Tests
dotnet test --project tests/Leeway.Analyzers.Tests
python scripts/package-check.py
```

## Generator

For each class with merge attributes, it emits a schema, replacing reflection. For a client entity, it also emits a typed API, so a wrong kind of change no longer compiles:

```csharp
public class Zone : OfflineEntity
{
    [Escrow(Min = 0, Lease = 10)] public int RemainingCapacity { get; set; }
    [Counter]                     public int CheckIns { get; set; }
    [LastWriterWins]              public string? Notes { get; set; }
}

await client.TrySpendRemainingCapacityAsync("north", 1);
await client.AddCheckInsAsync("north", 1);
await client.SetNotesAsync("north", "Turnstile 3 jammed");
```

Snapshots of the generated code are committed: `tests/Leeway.Generators.Tests/*.verified.cs`. I read them before accepting them. The tests also check:

- The generated code compiles with no warnings, for public, internal, nested, inherited, partial, and no-namespace cases.
- An unrelated edit does no new generator work.
- In `tests/Leeway.Integration.Tests`, generated code really runs: the generated schema is the one used, it agrees with reflection field by field, and the typed API works end to end over Datasync.

## Analyzer

| Rule | Severity | What it catches | Code fix |
|---|---|---|---|
| LEE001 | Warning | A numeric entity field with no merge attribute is decremented | Add `[Escrow]` or `[Counter]` |
| LEE002 | Warning | A merged field is assigned directly | None |
| LEE003 | Error | A merge attribute on an unsuitable property | None |
| LEE004 | Error | More than one merge attribute on a property | None |
| LEE005 | Warning | A merge attribute outside an entity | None |
| LEE006 | Warning | `[Escrow]` with a lease that grants nothing | None |

The code fix tests cover both attributes, adding a missing `using`, keeping comments and existing attributes, and a property in another file. Each rule also has tests for what it must not flag. An early draft of the fix hard-coded Windows line endings, which the tests caught.

## The packages work

An in-process test cannot show that a generator loads from a NuGet package. `scripts/package-check.py` packs the libraries, then builds an outside project against them, with its own private package folder. CI runs it too. From the check's first manual form:

```
Zone.cs(33,9): warning LEE001: 'Unprotected' is decremented but has no merge attribute
Zone.cs(34,9): warning LEE002: 'Notes' is a merged field, so a direct write is lost or refused
Build succeeded.
```

The build succeeding is itself the proof for the generator, because that project calls `client.TrySpendRemainingCapacityAsync`.

## CI found a race in Datasync

The first CI run of this milestone failed one test on Linux, with `ObjectDisposedException` from inside Datasync's sync lock, in a probe with no Leeway code involved. Reading the source showed a real race, explained in `docs/design/datasync-integration.md`. It needs several contexts in one process, which parallel tests had, and so would a real app with several stores. I could not reproduce it on demand, so **the evidence is one stack trace plus the code**.

The fix on Leeway's side is `LeewaySyncGate`, which lets one sync run at a time in a process, with a deterministic test. I also reported it upstream as [#596](https://github.com/CommunityToolkit/Datasync/issues/596).

## ADR-0015's promises

| M5 was to | Result |
|---|---|
| Generate the schema instead of reflecting | Done, with reflection as the fallback for a class the generator did not process |
| Offer a friendlier API | Done, as `client.TrySpendRemainingCapacityAsync`. The `zone.TrySpendAsync` form would need an entity to hold a client, and it does not |
| Try `ISet<string>` | Tried. EF Core refuses it without a value converter: `HashSet<string> cannot be used as a primitive collection`. A converter might work, and OData would need testing too. Sets stay as JSON strings for now |

## Limits

- **Not NativeAOT-ready.** Registers still use reflection-based `System.Text.Json`, and Datasync may have its own limits. Nothing here has been run under AOT.
- **LEE001 is a heuristic.** It only looks at entity classes, and only at decrements it can see.
- **The client and server classes are still not compared.** A mismatch of attributes is not caught at build time.
- **The analyzer's rules are new.** Their false-positive rate on real code is unknown, because no real project has used them. The tests are all small snippets.
- **Generic classes get nothing, and abstract ones get no schema of their own.** Nested classes get a schema but no typed API.
- **The code fix has been tested through Roslyn's test harness,** not in Visual Studio or Rider.
- **The generated method names can collide** with a field whose name makes the same method. That is unlikely, and it has no special handling.
